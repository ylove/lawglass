# Lawglass threat model

**Status of this document:** written for rc.3 (issue #178), from two independent audits of `fb663d1` (v0.1.0-rc.2) and a re-check of the code at the time of writing, and brought up to date for v1.0.0. It describes what the code does today. Planned work is marked as planned. The open items are the budgets in core (#181), the remaining public-mode work (#180), cancellation into index upserts (#221), the cross-process store (#222), supply chain (#186), scanned redline pixels (#193) and the MCP section.

Standards we review against: OWASP ASVS 5.0 L2, the OWASP Top 10 for LLM Applications 2025, the CWE Top 25, NIST SSDF and OpenSSF Scorecard. These are review targets. We do not claim compliance. The control matrix that maps each requirement to evidence is a separate document, still to be written (#189).

## How to read the status column

| Status          | Meaning                                                                                             |
| --------------- | --------------------------------------------------------------------------------------------------- |
| **Mitigated**   | A control exists in the code on this branch. The evidence column names the file. A test covers it.  |
| **In progress** | A fix is filed or under way. The evidence column names the issue.                                   |

## 1. System overview

Lawglass is a localhost-first legislation question-and-answer tool. You give the CLI one legislation URL. It fetches the document, parses its structure (including struck and inserted amendment text), indexes it, and answers questions with citations to section, page and line. A local web UI and an optional public mode sit on the same server.

```
 browser ──HTTP──▶ local server (Hono) ──▶ pipeline ──▶ fetcher ──▶ legislation URL
                        │                      │
                        │                      ├─▶ parsers (PDF, XML, HTML)
                        │                      ├─▶ index (local files, or Pinecone)
                        │                      └─▶ LLM provider (Anthropic, OpenAI, Google, claude-cli)
                        └─▶ ~/.lawglass  (config, registry, documents, caches, indexes)
```

The primary deployment is one person on one machine. Public mode (`serve --public`) is a demonstration of a hosted design. It is not deployed.

A hosted private preview runs `serve --private` on one Cloud Run instance at lawglass.xyz. Only people with an invite link can use it. Section 2.9 and ADR 0014 cover it.

### Assets

| Asset                                | Why it matters                                                                                                                                       |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Provider keys**                    | Anthropic, OpenAI, Google and Pinecone keys belong to the user. A leaked key costs money and exposes the user's account.                             |
| **The user's machine, disk**         | The tool fetches attacker-chosen URLs, parses attacker-chosen bytes and writes to `~/.lawglass`. It must not become a route to other files or hosts. |
| **Integrity of explanations**        | The product exists so that struck text is never read as current law, and so that every claim points to a real section. A wrong answer is the harm.   |
| **Availability of the local server** | A hostile document or page should not freeze or crash the user's server, or fill their disk.                                                         |
| **The operator's budget**            | In public mode, the host pays for model calls, embeddings and storage. Anonymous visitors must not be able to run that up.                           |
| **The access key**                   | In the hosted preview, the invite key is the only thing between the internet and the full app, and the operator's model budget behind it.            |

### Actors

- **The user is trusted. The document is not.** Legislation text, PDFs and pages can carry markup, hostile structure and prompt-injection text.
- **Other web pages in the user's browser are not trusted.** They can try to call the local server.
- **Other local users and processes are partly trusted.** They share the machine and possibly `~/.lawglass`.
- **Public visitors are anonymous and not trusted.**
- **Invited visitors to the hosted preview are partly trusted.** They hold the access key, but their documents and questions are treated like any other untrusted input, and their use is capped.
- **Model output is untrusted.** It is never used as markup, a URL to fetch or a command.
- **The supply chain is partly trusted.** We pin and verify what we can.

## 2. Trust boundaries

Each boundary has a STRIDE table (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege). Rows give the threat, an example at the level of the attacker's goal, the mitigation, the status and the evidence. Issue numbers refer to the `ylove/lawglass` repository. Audit finding IDs (G1 to G25, N1 to N14, C1 to C7) come from the pre-rc.3 audits.

## 3. Residual risk we accept

- **Citation existence is checked. Claim support is not** (N14). A hostile document can steer wording. The citation drawer lets the reader check the source text. The README should say "validated citations", not "verified claims".
- **Document text goes to the user's chosen provider.** The user picks the provider and can use the local backend.
- **A same-user attacker is inside the boundary.** We harden against other local users and other web pages, not against the account owner's own processes.

## 4. Out of scope for this round

- **Opening the hosted site to anonymous visitors.** The hosted preview is invite-only (section 2.9). Serving anonymous visitors needs the public-mode work in section 2.7 (#180) first, plus a WAF or rate limits at the edge.
- **Third-party services' own security:** the providers, Pinecone, GovInfo and Cloudflare.
- **Physical access and a compromised operating system.**

## 5. How to report a vulnerability

Report privately. Do not open a public issue for an exploitable finding. See `SECURITY.md` for the channel, supported versions and response targets. It uses GitHub's private vulnerability reporting on the repository's Security tab.

## 6. Keeping this document current

- Change a status only with evidence: a file path, a test, a CI job or a merged PR.
- When an open issue lands, move its rows to Mitigated and cite the file, the test and the PR. The advisory for the parser limits will be published with v1.0.0; once it is out, replace "parser resource limits" with the public detail.
- The delta audit (#190) re-checks the OCR raster decoder, the WASM files, the scenario endpoint, the delegations chip and any MCP server.
