# Jurisdictions roadmap

This document is the plan for making Lawglass read legislation from all 50 U.S. states. It records what each legislature publishes, how its bills mark changes to existing law, and what work each state needs. `docs/spec.md` stays the source of truth for behavior; this file is the roadmap and the research behind it.

## What "supported" means

A jurisdiction is supported when all of these hold:

1. **The URL resolves to official full text.** A reader pastes one URL, either a bill page or a bill text. Lawglass finds the official text of the bill from that URL. Text comes only from the legislature (or the official publisher for it), keyless, never from an aggregator such as LegiScan, Open States or FastDemocracy.
2. **Sections are parsed.** The document is split into sections so answers can cite them. Page and line citations are available for PDFs and other sources with printed line numbers; XML and HTML sources fall back to section-only citations (spec amendment 7).
3. **Change marks are read correctly.** The parser knows which words the bill removes from current law and which it adds. Repealed text is never presented as current law. Where a document has no marks at all (instruction-only bills, or a scan whose marks could not be read), the answer says so rather than claiming "no changes".

## State by state

### How to read the tables

**Evidence column.** Each convention claim carries a tag.

- **Legend**: the legislature's own legend sentence was found in a sampled bill and is quoted.
- **Observed**: seen in the sampled file (tags, CSS classes or bracket characters), but no legend sentence.
- **Inferred**: a PDF text layer with no bracket characters and no legend across five sampled introduced bills. That points to drawn strike and underline lines but does not prove it. Confirm with the geometry parser before relying on it.
- **Unverified**: nothing usable was obtained (site is a script-rendered shell, blocked, or the sample had no amendments).

**Samples.** Introduced versions of one to five bills per state from the 2025 or 2026 session. A bill that only creates new law has no marks, so a missing legend does not mean a state has none.

**Status.** Every state not listed as Supported or Next is "Planned". The blocking work names the family above plus anything state-specific.

### Patterns across the states

- **PDF is the common denominator.** Most states publish a PDF of each bill version. HTML text exists in about a dozen (AZ, DE, FL, MI, MN, NH, NJ, NY, PA, SC, TX, WA, WV). Where HTML exists it is the better source, because marks are tags rather than drawn lines.
- **Script-rendered sites are the hard cases.** GA, IN, MT, VA and SD serve a JavaScript shell for the bill page. The text URL is not derivable from the bill number alone, so the resolver must call the site's own data endpoint (as New Jersey's does) or find a stable document path.
- **Blocked to automated fetch.** CA and HI answered 403 (and `www.nysenate.gov` answers a Cloudflare challenge). FL answers 429 under rapid requests. These need a fetch policy decision before any parser work, and a hosted deployment may be blocked where a laptop is not.
- **Internal ids.** DE, NH, NV, LA, NE and PA bill pages hold an internal id or printer's number that the text URL needs. A reader's pasted URL already contains it; a bare bill number does not.
- **Session numbering differs.** Examples: Iowa `ga=91`, Colorado `2025A`, Oregon `2025R1`, Tennessee `GA=114`, South Carolina `sess126`, Vermont `2026` for the 2025-26 biennium, New Jersey `2026` for the 2026-27 session.

## New York

Supported since v1.1 (#281, #282); `docs/new-york-bills.md` records the source checks and real-bill accuracy. New York text is reachable keyless, with one obstacle: the Senate's own site is behind a challenge, so its bill pages are mapped to the Assembly text or the Senate PDF and never fetched.

- **Marks.** Legend on every bill: "EXPLANATION--Matter in italics (underscored) is new; matter in brackets [ ] is old law to be omitted." In Assembly HTML, new text is `<B><U>...</U></B>` and removed text is `[<B><S>...</S></B>]`, so the deleted words sit inside literal brackets and a strike tag. In the Senate PDF the text layer holds the brackets and the underline is drawn.
- **Fetch.** `legislation.nysenate.gov/pdf/bills/<year>/<S|A><n>` and `nyassembly.gov/leg/?bn=...` both work keyless. `www.nysenate.gov` bill pages are blocked (403 with a Cloudflare challenge). The Open Legislation API at `legislation.nysenate.gov/api/3` returns `A valid API key is needed` (HTTP 401, error code 701), so it cannot be a keyless source.
- **Format family.** F3. The bracket convention turns on only when the legend sentence is present; bracketed runs become deleted text before sections are detected.

## New Jersey (next)

New Jersey's bill page is a script-rendered Next.js app, but the site's own JSON endpoints are keyless and give exact text URLs.

- **Marks.** Legend (printed on the PDF's last page, not in the HTML): "EXPLANATION - Matter enclosed in bold-faced brackets [thus] in the above bill is not enacted and is intended to be omitted in the law. Matter underlined thus is new matter." HTML text uses `<u>` for new words and bold `[` `]` spans for deleted words, with a bold superscript number marking which amendment made each change.
- **Fetch.** `GET https://www.njleg.state.nj.us/api/billDetail/billText/<bill>/<session>` returns the list of text versions with `HTML_Link` and `PDFLink`. Prior sessions use `billDetailHist`. The files live under `https://pub.njleg.gov/Bills/<session>/<bill>/<number>_<version>.HTM`.
- **Format family.** F3, same bracket rule as New York, plus superscript amendment numbers to strip.

## How to add a state

1. **Resolver.** Add a source that maps the pasted bill page URL or bill text URL to the official text URL, in the same shape as the Ohio and federal resolvers. Cover every URL a reader might paste: bill page, text link, and any alternate host. Return the bill number, session and title where the source gives them.
2. **Host allowlist.** Add the exact hosts to `DEFAULT_INGEST_HOSTS` in `src/server/ingest-hosts.ts` and the history allowlist where the state has a history source. Allow only the hosts the resolver reads. Remember the hosted deployment has its own allowlist variable and needs the same update.
3. **Parser family.** Pick the family from the tables. If the family already has a parser (F2), the work is wiring the right file format. If not (F3 to F6), build the family's rule once, behind a small explicit function, and reuse it for every state in the family.
4. **Metadata.** Fill the bill number, chamber, session and sponsors from the official source. Keep the text source and the metadata source separate so a metadata outage never blocks reading the bill.
5. **Tests.** Add a synthetic sample under `tests/synth/` that reproduces the state's mark convention (CI never uses real legislation). Add a local-only test against a real bill downloaded by `scripts/fetch-fixtures.ts` into the gitignored `fixtures/downloads/`; it skips when the file is absent. Cover a bill that amends existing law, a bill that only adds new law, and a bill with a repealed section.
6. **Fetch behavior.** Check the site with a plain request. If it answers 403 or 429, record that in this document and decide the fetch policy before parser work.
7. **Hosted allowlist.** Update the hosted deployment's host allowlist and re-run the hosted smoke test.
8. **Docs.** Update the row in this file, move the state's status, and note the sample bills used.

## Verified on

Researched on 2026-10-26 from a laptop (macOS, residential network) with `curl` and a browser user agent. Bill pages and text were fetched for the states above; headers and content types were checked, and for PDFs the text layer was extracted to look for legends and bracket characters. "Inferred" entries rest on five sampled introduced bills per state and need confirmation with the geometry parser. Legislature sites change URLs often (Illinois and Kansas already redirected old patterns), so treat the patterns as a starting point and re-check before building each resolver. A hosted deployment may see 403 or 429 responses that a laptop does not.
